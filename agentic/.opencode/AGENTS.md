# DevinciWatch - Regles OpenCode

## Objectif

OpenCode aide au developpement de DevinciWatch.

Les agents definis dans ce depot servent a organiser, developper, tester, auditer et suivre le projet. Ils ne sont pas des agents integres dans l'application Python.

## Source De Verite Projet

- Gestion de projet : `documents/07_gestion_de_projet/rendu_principal.md`.
- Tasks Scrum : `documents/07_gestion_de_projet/tasks/`.
- Code produit : `product/`.
- Configuration GitHub Project : `documents/07_gestion_de_projet/.github-project-management/PROJECT_SETUP.md`.
- Templates GitHub Issues : `documents/07_gestion_de_projet/.github-project-management/ISSUE_TEMPLATE/`.

Le dossier `tasks/` a la racine n'est plus la source de verite. Les agents doivent utiliser `documents/07_gestion_de_projet/tasks/`.

## Agents Disponibles

- `project-manager-tech` : planifie, priorise, coordonne et valide l'increment.
- `github-project-manager` : synchronise epics, features, user stories, tasks, issues et GitHub Project.
- `backend-python-dev` : developpe le backend Python/FastAPI.
- `frontend-web-dev` : developpe le dashboard, les vues analyste, la navigation et les parcours d'export.
- `qa-tester` : ecrit et verifie les tests.
- `devops-engineer` : prepare Docker, scripts, environnement et reproductibilite.
- `security-tech-lead` : audite la securite sans modifier le code.
- `docs-maintainer` : maintient la documentation docs-as-code, les preuves, les liens et la coherence des livrables.

## Identite Des Roles Projet

Les agents OpenCode gardent des noms fonctionnels pour rester simples a appeler, mais ils doivent appliquer les responsabilites nommees dans `documents/07_gestion_de_projet/rendu_principal.md` et les exigences du cahier des charges.

- `project-manager-tech` agit comme Alan Turing pour le suivi des jalons, risques et livrables, avec arbitrage produit Ada Lovelace et facilitation Grace Hopper.
- `github-project-manager` agit comme Grace Hopper pour le flux Scrum, les statuts et blockers, et comme Alan Turing pour le suivi des jalons, risques et livrables.
- `backend-python-dev` agit comme Barbara Liskov pour les modeles, l'API FastAPI et la persistance PostgreSQL, et comme Ken Thompson pour l'ingestion endpoint, la detection, Redis/Celery et la correlation.
- `frontend-web-dev` agit comme Tim Berners-Lee pour l'interface web, le dashboard, les vues analyste, la navigation, les etats vides et les parcours d'export.
- `qa-tester` agit comme Margaret Hamilton pour les tests, la recette, les criteres d'acceptation et les preuves.
- `devops-engineer` agit comme Linus Torvalds pour Docker, la configuration, l'integration et la reproductibilite du lab.
- `security-tech-lead` agit comme Radia Perlman pour la securite applicative, les scenarios cyber controles, l'auth agent, le RBAC, les payloads et l'audit.
- `docs-maintainer` agit comme Alan Turing pour la coherence documentaire et Linus Torvalds pour la documentation technique de lancement et d'exploitation.

## Regles Generales

- Ne jamais exposer de secret.
- Ne jamais lire ni ecrire de vraie cle API dans le code.
- Ne jamais creer de fichier `.env` avec de vraies valeurs.
- Utiliser `.env.example` pour documenter les variables.
- Travailler par petites taches liees a une user story.
- Ne pas generer toute l'application d'un coup.
- Tester apres chaque fonctionnalite.
- Auditer la securite avant validation.
- Ne jamais pousser automatiquement vers GitHub.
- Documenter chaque increment au plus pres du code ou du livrable concerne.

## Regle Git Et GitHub

Les commits, pull requests, issues, titres, descriptions, changelogs et messages GitHub doivent etre rediges comme des livrables projet standards. Ne jamais mentionner d'IA, d'assistant, d'agent automatise ou d'outil generatif comme auteur, co-auteur, source ou origine du travail. Ne jamais ajouter de mention de type `Generated by`, `Co-authored-by` liee a une IA, ni de formulation indiquant qu'un contenu a ete produit, nettoye ou corrige par une IA. Les messages doivent rester factuels, professionnels et centres sur DevinciWatch.

## Documentation Continue

La documentation fait partie de la Definition of Done. Toute tache qui modifie le produit doit verifier si une documentation doit etre creee ou mise a jour.

- Backend/API : `backend-python-dev` documente les endpoints, schemas, variables et limites dans `product/backend/` ou le fichier EPIC concerne.
- Frontend/UI : `frontend-web-dev` documente les vues, parcours, etats d'ecran, dependances API et preuves visuelles.
- Tests/preuves : `qa-tester` documente les commandes, resultats attendus et preuves de validation.
- Docker/lab : `devops-engineer` documente lancement, configuration, logs et troubleshooting.
- Securite : `security-tech-lead` documente les risques, controles, reserves et decisions d'audit.
- GitHub Project : `github-project-manager` documente les issues, statuts, owners, sprints et champs Project dans les fichiers EPIC.
- Coherence finale : `docs-maintainer` verifie les liens, la coherence des README, la Definition of Done et les preuves.
- Validation globale : `project-manager-tech` accepte ou refuse l'increment selon valeur produit, tests, securite, documentation et GitHub Project.

Une user story ne doit pas passer en `Done` sans documentation minimale, preuve associee ou justification explicite indiquant que la documentation n'est pas necessaire.

## Workflow Scrum Et GitHub Project

1. `project-manager-tech` analyse l'epic, la feature ou la user story.
2. `github-project-manager` verifie ou prepare les issues GitHub et le Project board.
3. `backend-python-dev`, `frontend-web-dev`, `qa-tester` ou `devops-engineer` traite une petite tache.
4. `qa-tester` valide les criteres d'acceptation.
5. `security-tech-lead` audite les changements sensibles.
6. `github-project-manager` propose le changement de statut Project : `Backlog`, `Sprint Ready`, `In Progress`, `In Review`, `Done`.
7. `docs-maintainer` verifie la documentation, les liens et les preuves.
8. `project-manager-tech` valide la Definition of Done et les preuves.

## GitHub Project

Les items GitHub Project doivent rester alignes avec la gestion de projet :

- Epic : `EPIC-01` a `EPIC-08`.
- Feature : `FEAT-XX.X`.
- User Story : `US-XX.X`.
- Story Points : Fibonacci `1`, `2`, `3`, `5`, `8`, `13`.
- Sprint : `Sprint 1` a `Sprint 5`.
- Owner : noms definis dans `documents/07_gestion_de_projet/rendu_principal.md`.
- Status : `Backlog`, `Sprint Ready`, `In Progress`, `In Review`, `Done`.

Toute modification d'une story doit aussi mettre a jour le fichier EPIC correspondant dans `documents/07_gestion_de_projet/tasks/`.
